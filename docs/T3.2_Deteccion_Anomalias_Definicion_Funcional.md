# T3.2 – Detección de Anomalías Energéticas (MASAI)

**Líder:** EXOS | **Periodo:** M10–M28
**Modo de desarrollo:** aplicación independiente, en paralelo al módulo de monitorización y gestión de energía (integración posterior)

---

## 1. Qué hace la aplicación

Módulo de detección de pérdidas de eficiencia energética que analiza series temporales de consumo y genera alertas cuando detecta situaciones anómalas, clasificándolas y explicando su causa probable. Combina un sistema experto basado en reglas con un modelo de Deep Learning no supervisado, fusionados en un motor híbrido. Su salida (alertas, causas, recomendaciones) está pensada para alimentar el módulo de Gestión de la Mejora y las herramientas de trazabilidad de incidencias de MASAI, aunque en esta fase se desarrolla desacoplada de esos módulos.

## 2. Funcionalidades incluidas

### 2.1 Motor de reglas (sistema experto)
- Editor de reglas para el responsable de energía: umbrales estáticos, umbrales dinámicos (% desviación sobre baseline histórico por turno/producto/receta), reglas compuestas (ej. "consumo de horno > X durante Y minutos con producción parada").
- Evaluación programada (near-real-time) sobre el histórico, con agregación adaptativa por tipo de variable.
- Versionado de reglas y trazabilidad de qué regla disparó cada alerta.

### 2.2 Motor de Deep Learning no supervisado
- Modelo de detección de anomalías (autoencoder / Isolation Forest como baseline) entrenado por línea/equipo/EnPI, sin etiquetas previas.
- Reentrenamiento periódico (batch) para adaptarse a drift estacional/productivo.
- Score de anomalía continuo, con explicabilidad básica (qué variables contribuyen más a la desviación).

### 2.3 Motor híbrido
- Capa de fusión: combina score del modelo DL con el resultado de reglas para reducir falsos positivos y detectar anomalías nuevas no cubiertas por reglas escritas.
- Priorización de alertas por confianza + impacto energético estimado (kWh/€).

### 2.4 Gestión de alertas
- Bandeja de alertas con estado (nueva/en revisión/confirmada/descartada), asignación a responsable.
- Feedback del usuario (confirma/descarta) que retroalimenta el ajuste de reglas y el reentrenamiento del modelo DL (human-in-the-loop).
- Integración futura con la trazabilidad de incidencias de MASAI.

## 3. Qué NO hace (fuera de alcance)

- No hace control activo ni actuación automática sobre equipos (solo detecta y notifica).
- No es un gemelo digital de simulación física.
- No hace mantenimiento predictivo de fallos mecánicos como objetivo propio.
- No sustituye las reglas de negocio de la capa MES/MOM existente; se integrará sobre ella, no la reemplaza.
- El modelo DL no es una IA generativa/LLM (eso corresponde a otras tareas de MASAI).

## 4. Modo de desarrollo: desacoplado

- **Ingesta de datos:** T3.2 no lee directamente de las hipertablas de producción del módulo de monitorización. Usa su propia fuente de datos (dataset histórico exportado/replicado, o simulado si no hay histórico suficiente).
- **UI de alertas:** interfaz propia, no embebida en el frontend del módulo de monitorización en esta fase.
- **Motor híbrido:** se diseña y valida contra el dataset propio.
- **Se reutiliza:** tecnología de series temporales (TimescaleDB, patrón de continuous aggregates y agregación adaptativa), semántica de EnPI/jerarquía de equipos/normalización por producto-turno-receta, diseño de reglas y de la capa de fusión híbrida, stack backend (Java/Hibernate + Python/FastAPI).
- **Integración futura:** hito explícito posterior — cuando el módulo de monitorización esté disponible, T3.2 cambia su fuente de datos de dataset propio a las hipertablas reales, y la UI se embebe en la plataforma MES/MOM.

## 5. Datos a manejar

- Series temporales de consumo energético (eléctrico, gas, agua, aire comprimido).
- Contexto de producción (orden, producto/receta, turno, operario) para normalizar el consumo.
- EnPIs (indicadores de eficiencia energética).
- Metadatos de equipo (jerarquía de centros/equipos, potencia nominal).
- Histórico de alertas y feedback del usuario (para reentrenamiento y medición de precisión).
- Reglas versionadas (definición + histórico de disparos).

- Carga batch periódica si hay acceso puntual a datos reales de algún piloto.

### 6.3 Punto de acoplamiento futuro

Opción recomendada: vista materializada / réplica lógica desde las tablas reales del módulo de monitorización hacia este esquema (mapeo `Medida`→`medida`, `centropropiedad`→`propiedad_energetica`, `centro`→`centro_energetico`). Cero cambios en T3.2, solo un job de sincronización.

Descartado por ahora: API REST/streaming (Kafka) — sobredimensionado si ambos módulos acabarán compartiendo instancia TimescaleDB.

### 6.4 Reglas del contrato

- `centro_id`/`propiedad_id` son claves de negocio estables definidas por T3.2, no las PKs internas de MESView.
- Toda medida sin `contexto_produccion` vigente se marca como no normalizable, no se descarta.
- El motor DL debe tolerar huecos de datos, no asumir muestreo regular.

## 7. Tecnologías propuestas

- **Base de datos:** TimescaleDB (instancia/esquema propio en esta fase), reutilizando el patrón de continuous aggregates y agregación adaptativa ya probado.
- **Motor de reglas:** Java/Hibernate (o Drools si la complejidad de reglas compuestas lo justifica).
- **Motor DL:** Python (PyTorch/TensorFlow) para entrenamiento offline, servido como microservicio REST (FastAPI).
- **Orquestación de reentrenamiento:** batch job (cron / Airflow si la escala lo justifica).
- **UI de alertas:** interfaz propia (a definir), independiente del frontend JSF/PrimeFaces en esta fase.

## 8. Decisión de arquitectura: servicios separados

Se opta por estructurar el proyecto como **dos servicios independientes**: backend Java (reglas, motor híbrido, UI, persistencia) y microservicio Python/FastAPI (entrenamiento y scoring DL), comunicados por API REST.

**Justificación**

- **MLOps:** un pipeline de actualización del modelo DL (entrenamiento → validación → registro → despliegue → monitorización de drift) necesita desplegarse de forma independiente del resto de la aplicación. El microservicio Python es la unidad natural que un pipeline MLOps gestiona (contenedor versionado, endpoint de scoring estable, registro de modelos tipo MLflow) sin forzar rebuild/redeploy del backend Java en cada reentrenamiento.
- **Coherencia con la hoja de ruta técnica de MASAI:**
  - Infraestructura CI/CD ya prevista en el proyecto — pipelines separados para Java y Python es el estándar de la industria.
  - Enfoque cloud native (Docker/Kubernetes) del proyecto, que exige escalabilidad independiente entre componentes.
  - Evolución hacia microservicios ya apuntada en diseños recientes (módulo `svc-energy`) de cara a despliegues SaaS.
- **Alineación con el reparto de responsabilidad EXOS/CETECK:** la frontera entre servicios coincide con la frontera de aportación de cada socio (CETECK en modelos predictivos, EXOS en integración y valor de negocio).

**Mitigación de los inconvenientes iniciales**

- **Sobrecarga de prototipado en equipo pequeño:** orquestar ambos servicios localmente con un `docker-compose.yml`, evitando la complejidad de Kubernetes hasta que el proyecto lo requiera.
- **Contrato API entre servicios:** documentado con OpenAPI (Swagger) desde el inicio, como acuerdo vinculante único entre CETECK y EXOS para trabajar en paralelo sin romper integraciones.

## 9. Módulos por servicio

### `svc-energy-rules` (Java)
1. Ingesta/persistencia — carga del dataset propio (§6.2), esquema TimescaleDB del contrato de datos (§6.1).
2. Motor de reglas — CRUD de reglas, evaluación programada, versionado.
3. Cliente scoring DL — consumidor del endpoint OpenAPI de `svc-energy-dl`.
4. Motor híbrido/fusión — combina score reglas + score DL, calcula confianza e impacto.
5. Gestión de alertas — bandeja, estados, feedback del usuario.
6. UI — bandeja de alertas, editor de reglas.

### `svc-energy-dl` (Python/FastAPI)
1. Entrenamiento — job batch, autoencoder/Isolation Forest baseline.
2. Registro de modelos — versionado (MLflow o similar), promoción a producción.
3. Scoring — endpoint REST que expone el modelo activo.
4. Monitorización de drift — trigger de reentrenamiento.

### Transversal
7. Contrato API (OpenAPI/Swagger) entre ambos servicios.
8. Orquestación local (`docker-compose.yml`).

## 11. Análisis de viabilidad — modelos DL (Fase 3)

Análisis del código aportado (`data_loader.py`, `models.py`, `trainer.py`, `evaluator.py`, dataset SKAB) como candidato de baseline para `svc-energy-dl`.

**Encaje general:** alto. `reconstruction_error_per_variable()` (en `ConvAE`/`LSTMAE`) y `build_expert_interface()` (en `evaluator.py`) ya producen exactamente la interfaz que necesita el motor híbrido (§2.3): score continuo + flag por variable. `trainer.py` ya integra MLflow (`log_params`/`log_metrics`/`log_model`), base de la Fase 5.

**Qué encaja directamente**
- ConvAE y LSTMAE como candidatos de baseline no supervisado (§2.2); ConvAE como punto de partida (mejor F1 según referencia SKAB en el propio código).
- `reconstruction_error_per_variable()` cubre la explicabilidad básica por variable pedida en §2.2.
- MLflow cubre registro de experimentos y versionado de modelo (Fase 5).

**Qué falta para encajar en el contrato de datos (§6)**
1. `SENSOR_COLS` hardcodeado a las 8 variables de SKAB — debe generalizarse para construir el vector de features desde `propiedad_energetica` filtrado por `centro_id` (variables dinámicas por equipo).
2. No hay `contexto_produccion` en el pipeline — sin normalizar por turno/producto/orden, el modelo puede confundir "parón de producción" con "eficiencia", crítico antes de entrenar con datos reales.
3. Falta capa de servicio (FastAPI) — actualmente es training/evaluación offline, no un servicio con endpoint de scoring (módulo 3 de `svc-energy-dl`, §9).
4. Bug en `evaluator.py::evaluate()`: la rama `if train_errors is not None` para `threshold_per_var` no usa `train_errors`, duplica la lógica de la rama `else`. El umbral por variable siempre sale del test normal — corregir antes de fiarse de los umbrales que alimentan al sistema experto.
5. `fit_scaler` usa un único `MinMaxScaler` global — con múltiples `centro_id` de naturaleza distinta (horno vs compresor) mezclará rangos no comparables; debe ser por `centro_id` o `tipo_equipo`.
6. Sin lógica de promoción de modelo (registro → staging → producción) — pendiente para Fase 5, no bloqueante ahora.

**Veredicto:** viable como punto de partida de la Fase 3, no como producto final. Usar ConvAE como primer modelo, corrigiendo el bug del umbral y generalizando `SENSOR_COLS`/`scaler` al esquema del contrato de datos. La integración de `contexto_produccion` en la normalización es el bloqueante real antes de entrenar contra datos reales de EXOS.
