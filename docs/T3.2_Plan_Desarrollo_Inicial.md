# T3.2 – Plan inicial de desarrollo

Estado: propuesta de trabajo para validar con el equipo.

## 1. Objetivo de la primera entrega

Construir un vertical slice ejecutable que permita:

1. cargar un dataset desacoplado con medidas y contexto de producción;
2. persistirlo en TimescaleDB;
3. definir y evaluar reglas versionadas;
4. generar alertas trazables;
5. consultar las alertas mediante una API y una UI mínima;
6. dejar preparado el contrato OpenAPI para conectar posteriormente el scoring DL.

La primera entrega no debe intentar resolver todavía el reentrenamiento automático, la integración con MESView ni un sistema MLOps completo.

## 2. Situación actual del repositorio

Existe un prototipo Python sobre SKAB con ConvAE, LSTMAE, entrenamiento y registro en MLflow. Todavía no existen los servicios `svc-energy-rules` y `svc-energy-dl`, ni la base de datos, API, despliegue local o pruebas automatizadas del producto.

Hallazgos que deben entrar en el backlog técnico:

- `SENSOR_COLS` está fijado a SKAB y debe derivarse del catálogo de propiedades.
- El umbral por variable se calcula actualmente sobre el conjunto normal de test incluso cuando se reciben errores de entrenamiento.
- Las ventanas se crean sobre el DataFrame concatenado; pueden cruzar experimentos o centros distintos.
- El escalado global no es válido para centros/equipos con rangos físicos diferentes.
- No existe normalización con `contexto_produccion`.
- `reconstruction_error_per_variable()` devuelve un tensor, aunque su contrato documentado describe un diccionario.
- La evaluación puede fallar si las etiquetas solo contienen una clase al hacer `confusion_matrix(...).ravel()`.
- No hay tests unitarios, de integración ni de contrato.

## 3. Opciones de arquitectura

### Opción A – Dos servicios desde el inicio

`svc-energy-rules` (Java) contiene persistencia, reglas, fusión, alertas y API/UI. `svc-energy-dl` (Python/FastAPI) contiene entrenamiento y scoring. Ambos se ejecutan localmente con Docker Compose y se comunican mediante OpenAPI.

- Complejidad: media-alta.
- Testabilidad: alta si se mantienen adaptadores y contrato explícito.
- Escalabilidad: alta y alineada con el documento funcional.
- Operación: requiere coordinación de dos runtimes y versionado de API.
- Reversibilidad: alta; cada servicio puede evolucionar por separado.

### Opción B – Monolito Python para el MVP

API, reglas y scoring en un único servicio Python; TimescaleDB como persistencia. El motor DL se separa más adelante.

- Complejidad inicial: baja.
- Testabilidad: alta en la primera fase.
- Escalabilidad y reparto entre equipos: menor.
- Riesgo: puede retrasar la frontera Java/Python ya decidida y encarecer la migración.

### Opción C – Backend Java + entrenamiento Python offline

Java ejecuta reglas y alertas; Python solo produce modelos y artefactos, sin endpoint de scoring inicialmente.

- Complejidad inicial: media.
- Operación: sencilla durante el prototipo.
- Limitación: no valida pronto el contrato real entre servicios ni el scoring near-real-time.

### Recomendación

Adoptar la Opción A, pero implementarla mediante un MVP vertical: primero se despliega `svc-energy-rules` con reglas y un adaptador DL falso; después se sustituye el adaptador por `svc-energy-dl`. Así se respeta la arquitectura objetivo sin bloquear la entrega temprana por el modelo.

La elección definitiva debe registrarse como ADR una vez validada por el equipo.

## 4. Bloques de implementación

### B0 – Especificación y contratos

- Propósito: cerrar el contrato de datos, estados de alerta, reglas y errores.
- Dependencias: documento funcional T3.2.
- Salidas: especificación funcional versionada, OpenAPI inicial, ADR de arquitectura y decisiones abiertas.
- Riesgos: inventar semántica de unidades, severidad o impacto energético no confirmada.
- Tests: validación de ejemplos JSON/CSV y casos inválidos.
- Aceptación: otro desarrollador puede explicar entradas, salidas, errores y criterios de éxito sin leer código.

### B1 – Cimientos locales y datos

- Propósito: levantar TimescaleDB, migraciones y carga batch de CSV/Parquet.
- Requisitos: entidades `centro_energetico`, `propiedad_energetica`, `medida` y `contexto_produccion`.
- Salidas: `docker-compose.yml`, migraciones, índices, constraints y comando de importación idempotente.
- Tests: duplicados, UTC, calidad inválida, huecos, timestamps desordenados y contexto solapado.
- Aceptación: un dataset de ejemplo se carga desde cero y puede consultarse por centro, propiedad e intervalo.

### B2 – Motor de reglas y versionado

- Propósito: CRUD y evaluación determinista de reglas estáticas, dinámicas y compuestas.
- Salidas: modelo de regla, versiones inmutables, resultado de evaluación y trazabilidad.
- Tests: límites inclusivos/exclusivos, duración mínima, datos ausentes, reglas desactivadas y reevaluación idempotente.
- Aceptación: cada alerta identifica regla, versión, intervalo, valores observados y evidencia usada.

### B3 – Alertas y API/UI mínima

- Propósito: gestionar el ciclo de vida de alertas.
- Salidas: estados nueva/en revisión/confirmada/descartada, asignación, filtros, paginación y feedback.
- Tests: transiciones inválidas, concurrencia, filtros, autorización y errores de persistencia.
- Aceptación: un usuario puede consultar, asignar, confirmar y descartar una alerta conservando el histórico.

### B4 – Contrato y adaptador DL

- Propósito: aislar el motor híbrido del transporte y de la implementación del modelo.
- Salidas: cliente con timeout, validación de esquema, correlación de petición y tratamiento de error/timeout.
- Tests: respuesta válida, respuesta parcial, timeout, servicio no disponible, modelo no publicado y reintento controlado.
- Aceptación: el backend puede operar en modo reglas-only y registrar explícitamente la ausencia del score DL.

### B5 – `svc-energy-dl` baseline

- Propósito: convertir el prototipo SKAB en scoring por centro y propiedad.
- Salidas: pipeline reproducible, ConvAE baseline, artefacto de modelo, scaler y endpoint de scoring.
- Tests: ventanas por serie/centro, datos faltantes, variables dinámicas, consistencia de dimensiones y umbrales calculados solo con train normal.
- Aceptación: dado el mismo modelo y entrada, el endpoint devuelve score global, score por variable, versión de modelo y timestamps de referencia.

### B6 – Fusión, impacto y feedback

- Propósito: combinar reglas y DL, priorizar y cerrar el ciclo humano.
- Salidas: política de fusión versionada, confianza, impacto kWh/€ y realimentación.
- Tests: solo reglas, solo DL, ambos, conflicto, score ausente y datos sin contexto productivo.
- Aceptación: una alerta híbrida explica qué señales contribuyeron y por qué recibió su prioridad.

### B7 – MLOps e integración futura

- Propósito: promoción de modelos, drift, reentrenamiento e integración con hipertablas reales.
- Dependencias: B5 y B6 validados.
- Aceptación: despliegue reproducible, rollback de modelo y sincronización sin cambiar el contrato interno de T3.2.

## 5. Decisiones que deben cerrarse antes de B1/B2

- stack concreto del backend Java y mecanismo de UI;
- formato y tamaño del primer dataset piloto;
- frecuencia de muestreo y ventanas por tipo de variable;
- semántica exacta de `magnitud`, `incremental` y `discreto`;
- fórmula de baseline dinámico y tratamiento de cambios de producto/turno;
- estados y transiciones permitidas de una alerta;
- fórmula de confianza, impacto energético y prioridad;
- autenticación/autorización de la API;
- política de retención y calidad de datos;
- responsable de aprobar reglas y promover modelos.

Estas decisiones no deben quedar implícitas en el código.

## 6. Criterios de calidad transversales

- Todas las fechas se almacenan y transportan en UTC.
- Las claves `centro_id` y `propiedad_id` son de negocio y no dependen de PKs internas.
- Las medidas sin contexto se conservan y se marcan como no normalizables.
- Los endpoints validan entrada, devuelven un modelo de error estable y tienen timeout explícito.
- Las operaciones batch son repetibles e idempotentes.
- Cada requisito funcional importante se vincula a tests unitarios, de integración o de contrato.
- Las métricas del modelo se calculan separando entrenamiento, validación y test por serie/experimento, evitando fuga temporal.
- Toda alerta conserva evidencia suficiente para reproducir su evaluación.

## 7. Próximo paso recomendado

Ejecutar B0 como una sesión corta de cierre de contrato y, a continuación, implementar B1 y un primer endpoint de consulta de medidas. El siguiente bloque de código debería ser el esquema/migración y la carga batch, no todavía el autoencoder: sin datos contractuales y contexto productivo no se puede validar que el scoring represente eficiencia energética real.
